# software-tbc

Rust で書かれた**ソフトウェア Time Base Corrector（TBC）**です。

[English](README.md) | 日本語

software-tbc は RAW 映像のパイプの中（典型的には2つの FFmpeg プロセスの間）
に入り、アナログ／レガシー映像ソース（VHS、S-VHS、コンポジット出力のゲーム機、
劣化したキャプチャデバイス）の不安定な出力を、クリーンで正確なタイミングの
ストリームに変換します。処理するのは映像のみで、音声は FFmpeg 側で扱います
（[音声](#音声) を参照）。

主な機能:

- **フレーム同期（クロックドリフト推定つき）** — 入力のジッタ・ドリフト・
  ドロップをロックフリーのリングバッファで吸収し、正確な有理数レートの格子
  （30000/1001、25/1 など）で hold/drop または blend ポリシーにより再出力
  します。持続的なドリフトにはヒステリシス付きゲートで再ロックし、ノイズに
  追随せずソースクロックの変化にだけ追従します。
- **水平方向の行ジッタ補正** — VHS の典型的なアーティファクトである行ごとの
  水平位相の揺れを検出して除去します。精度は 1/256 ピクセルです。
- **ヘッドスイッチングノイズの隠蔽** — VHS キャプチャの下端のノイズ行を、
  その上のクリーンな行の複製または補間で覆います。
- **プロセッシングアンプ（プロックアンプ）** — ハードウェアのプロックアンプの
  つまみのように、輝度ゲイン、黒レベル（ペデスタル）、彩度、色相、ガンマ、
  クロマ遅延を調整できます。
- **信号断の検出と対処** — 入力が崩壊しても出力クロックは止まりません。
  最終フレームの保持、黒画面、テストパターンの代替、あるいは補正をバイパス
  した素通しのいずれかで出力し続けます。
- **ソース適応型の補正**（`--auto-adapt`）— 入力の輝度レンジ
  （リミテッド／フル）を分類し、ジッタ探索範囲をソースに合わせて実行時に
  適応させます。
- **実行時テレメトリと解析** — 構造化テレメトリ（JSON Lines または CSV）、
  信号断イベント、終了時サマリ。さらに、映像を書かずにソースをレポートする
  解析専用モードがあります。
- **幾何処理** — 入力／処理／出力のサイズを分離し、crop と padding が
  できます。アクティブピクチャがフレームを満たさないキャプチャに対応します。

## クイックスタート

```sh
cargo build --release
```

不安定なキャプチャを後処理する例です。コーデックは両側の FFmpeg が担当します。

```powershell
ffmpeg -i capture.mp4 -f rawvideo -pix_fmt yuv422p -s 720x480 -r 30000/1001 - |
  software-tbc --width 720 --height 480 --format yuv422p --preset vhs |
  ffmpeg -f rawvideo -pix_fmt yuv422p -s 720x480 -r 30000/1001 -i - -c:v libx264 out.mp4
```

RAW 映像にはメタデータがありません。サイズ、ピクセルフォーマット、
フレームレートはパイプの両側で明示し、software-tbc 自身の `--width` /
`--height` / `--format` と一致させる必要があります。software-tbc の出力
（テレメトリ、通知、エラー）はすべて stderr に出ます。stdout は映像バイト
専用です。フラグ省略時の既定値は 720×480、`yuv422p`、ボトムフィールド
ファースト、30000/1001 です。

## 対応フォーマットと規格

| ピクセルフォーマット（ワイヤ） | 備考 |
|---|---|
| `yuv422p`, `yuv420p`, `rgb24` | パイプラインのネイティブ形式（`yuv422p` はパックド YUYV バイト順） |
| `uyvy`, `yuyv` | 境界で変換 |
| `yuv420p10le`, `yuv422p10le` | 10ビット。内部では 8ビットに変換（制限事項を参照） |
| `nv12` | セミプラナー 4:2:0。境界で `yuv420p` と相互変換 |

`--standard` は幾何・レート・フィールド順序をまとめて設定します:
`ntsc`（720×480、30000/1001、BFF）、`pal`（720×576、25/1、TFF）、
`1080i`（1920×1080、30000/1001、TFF）。個別のフラグがこれを上書きします。

`--field-order` は `progressive`、`top-first`、`bottom-first` のほか
`auto` を受け付けます。auto ではフィールド順序をストリームから検出し、
検出がロックするまでは設定済みの順序をフォールバックとして使います。

入出力はヘッダなし RAW 映像です。stdin/stdout パイプ、単一の RAW ファイル、
ファイルシーケンス（パス内の `%`、例: `frames/frame_%06d.raw`）に対応します。
キャプチャデバイスへの直接対応はありません。キャプチャカードは FFmpeg
（Windows では `-f dshow` など）を前段にして供給してください。

## 仕組み

```
            ┌───────────── tbc-cli (software-tbc binary) ─────────────┐
            │  input thread → SPSC ring buffer → processing thread    │
            └──────┬──────────────────────────────────────┬─────────────┘
              FrameSource                            FrameSink      (tbc-io)
                   │                                        │
            ┌──────▼────────────────────────────────────────▼──────────┐
            │                      tbc-core                          │
            │  sync → head-switch mask → jitter → proc-amp → guard   │
            │  (pure transforms, no I/O, integer-ns timing)          │
            └────────────────────────────────────────────────────────┘

            tbc-sim: synthetic unstable-video generator + benchmarks
```

| クレート | 役割 |
|---|---|
| `tbc-core` | 信号処理パイプライン。I/O なし、スレッドなし、壁時計なし |
| `tbc-io` | `FrameSource` / `FrameSink` トレイト。RAW ファイル、stdio パイプ、ファイルシーケンス |
| `tbc-sim` | 劣化映像（ジッタ、ドリフト、ドロップアウト）の生成。実ハードウェアなしで TBC を測定するためのもの |
| `tbc-cli` | `software-tbc` バイナリ。CLI フラグ、TOML 設定、プリセット、パイプライン配線 |

設計の全体 — アルゴリズム、数式、性能予算、設定スキーマの完全な定義 — は
[SPEC.md](SPEC.md) にあります。

## プリセット

| プリセット | 想定ソース | バッファ | レートポリシー | 備考 |
|---|---|---|---|---|
| `vhs` | 劣化した VHS テープ | 12 フレーム | Blend | ジッタ補正 ±12px まで、ペデスタルをわずかに持ち上げ |
| `svhs` | S-VHS／比較的きれいなテープ | 8 フレーム | Hold/drop | ジッタ補正 ±8px まで |
| `unstable-composite` | 非常に不安定なコンポジットソース | 16 フレーム | Hold/drop | 信号断時はテストパターン、信号断タイムアウト 500ms |
| `low-latency` | ライブプレビュー／配信 | 2 フレーム | Hold/drop | ジッタ補正オフ。追加遅延は約2フレーム |

## 設定

すべてのパラメータは CLI フラグか TOML ファイル（`--config tbc.toml`）で
設定できます。レイヤーは次の順序で解決され、後ろのレイヤーが勝ちます:

```
defaults  →  preset  →  TOML file  →  --standard  →  individual CLI flags
```

日常的によく使うフラグ: `--preset`、`--standard`、`--format`、
`--field-order auto`、`--head-switch-lines N`（VHS のヘッドスイッチング
ノイズ隠蔽）、`--auto-adapt`、`--signal-loss
last-frame-hold|blackout|test-pattern|passthrough`、そして中心のずれた
キャプチャ向けの幾何フラグ群（`--input-width` …、`--crop-left` …、
`--pad-left` …）。完全な一覧は SPEC.md §6（CLI）と §7（TOML スキーマ）に
あります。`software-tbc --help` でも同じフラグを確認できます。

## ライブ運用

ライブキャプチャでは `--stamp wall-clock` を使ってフレームに到着時刻で
スタンプし、同期段が到着時刻から動作するようにします（既定の `nominal`
モードはフレームの並びとレートからタイムスタンプを導出するため、ファイル
処理向きです）。wall-clock モードでは**過負荷フォールバック**が出力レートを
守ります。処理が追いつかない場合、まずジッタ補正をスキップし、次に blend
から hold/drop へ落とします（`--no-overload-fallback` で無効化。段階は
プリセット依存で、`low-latency` には落とす段階が残っていません）。

信号断ポリシー（`--signal-loss`）:

| ポリシー | 信号断中の挙動 |
|---|---|
| `last-frame-hold` | 最後の正常フレームを繰り返す |
| `blackout` | 黒フレームを出す |
| `test-pattern` | テストパターンを出す |
| `passthrough` | 補正ステージをすべてバイパスして同期段のフレームを出す。推定器には入力されないため、状態は信号断の間も保持される |

`--fail-on-signal-loss` を付けると、信号断状態で終わった実行は終了コード
4 で終わります。

## テレメトリと解析

テレメトリは1秒ごとに stderr へ出ます（間隔は TOML の
`telemetry_interval_ms`）。内容はレイテンシ、バッファ充填率、
ドロップ／重複フレーム数、ドリフト（ppm）、再ロック状態、フレームごとの
処理時間とデッドライン超過回数に加え、信号断と復帰の即時イベント行と、
実行終了時の1行サマリです。`--telemetry-format csv` で固定24カラムの
CSV 形式に切り替わります（表計算／ログパイプライン向け）。

ソースを処理せずに調べたい場合は `--analyze-only` を使います。
パイプラインは破棄専用シンクに対して動作し、出力パスは開かれず、
stdout に JSON レポートが1行だけ出ます。内容はフレーム数、信号の有無、
ジッタ統計、ドリフト、観測された輝度レンジです。

```sh
software-tbc --analyze-only --input capture.raw --width 720 --height 480 --format yuv422p
```

終了コードは、最後まで信号があれば 0、信号断のまま終わった場合（または
入力が空の場合）は 4 です。

## 音声

software-tbc は音声に触れません。TBC は実時間の遅延（buffer/2 + 1 フレーム）
を加えるため、ライブ録画では FFmpeg 側で音声を遅らせる必要があります。
一方、ファイル処理ではタイムラインがフレームの並びから再生成されるため、
固定遅延は不要です。レシピ、遅延表、検証手順は
[examples/av-sync.md](examples/av-sync.md) にあります。

## 性能

参考測定値（リリースビルド、SD 解像度でのフルパイプライン、`tbc-sim` の
ベンチを共有仮想マシンで実行したもの。保証値ではなく目安です）:

| 規格 | 平均処理時間 | スループット | フレーム間隔 |
|---|---|---|---|
| NTSC 720×480 | 5.6 ms/フレーム | 178 fps | 33.4 ms |
| PAL 720×576 | 6.9 ms/フレーム | 145 fps | 40 ms |

控えめな共有 VM でも SD で実時間の約6倍の余裕があります。専用マシンでは
さらに速くなります。再現は
`cargo run --release -p tbc-sim --example bench` です。

追加遅延は `buffer_frames / 2 + 1` フレームです（既定は約5フレーム、
29.97fps で約167ms。`low-latency` は約2フレーム、約67ms）。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | 正常終了 |
| 2 | 設定エラー（フラグ、TOML、値の組み合わせ） |
| 3 | I/O エラー（入力が読めない、出力が書けない） |
| 4 | 信号断状態で終了（`--fail-on-signal-loss` 時、または解析専用モードで信号なしに終わった場合） |

## ステータスと制限事項

コア実装は**完了**しています。全8フェーズが実装され、テストスイートは
**159件**が通過します。往復品質テスト（合成的に劣化させたストリームが
補正で測定可能に改善すること）と、長時間のドリフトシミュレーションを
含みます。

検証済みなのは、合成入力と生成入力によるファイル／パイプ処理、および
Windows と Linux の CI 構成での動作です。**未検証**なのは、実際の
キャプチャデバイスと実テープを使った長時間の運用です。特に信号断の経路は、
ファイル入力では不正なフレームを作れないため、状態を強制した単体テストで
検証しています。software-tbc は実利用の評価に使える状態です。無人の本番
運用の前に、ご自身のキャプチャ環境で検証してください。

既知の制限:

- 内部処理は 8ビットです。10ビット形式は境界で変換されます（内部まで
  16ビット化するネイティブ対応は将来拡張。SPEC §10）
- 内部の `yuv422p` レイアウトはパックド YUYV バイト順です。互換性のため
  維持し、SPEC §3 に記載しています
- キャプチャデバイスからの直接入力はありません（FFmpeg を前段に
  使ってください）
- 出力のペーシングは入力駆動です。入力が止まれば出力も止まります
